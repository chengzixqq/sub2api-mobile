# UI 决策记录（Claude 方案）

> 逐轮问答的结果。每条写明来源轮次与用户原话要点；后续设计和实现以此为准。

## 产品形态

- **双风格应用**：先定“主模式”，后续再做“简化模式”（C 表格工作台那种，用于快速筛查大量数据）。主模式与简化模式共享数据、筛选、选中对象与动作。（2026-10-16）
- **配色**：游标 Vernier 石墨黑白，浅色 / 深色两套；字体、形状可按布局定。（2026-10-16）
- **主模式骨架**：A 收件箱——底部 4 个 Tab（今日 · 账号 · 用户 · 监控）+ 搜索，日志不占 Tab。B 的好看要吸收。（2026-10-16）

### 日志行的改动（用户原话整理）

- 金额、时间、首字 / 耗时像 B 一样**固定在右侧**。
- 右侧第一行：金额。
- 右侧另一行：`首字/耗时 · 时间`（例：`1.2s/3.2s · 09:41`）。用户原文两处都写“第一行”，按“金额第一行、时间那行在第二行”理解，第 2 轮对比页里请用户确认。
- **成功和失败的请求都要有二级详情页**：手机屏幕有限，行里放不下的字段都进详情。
  - 成功请求可用字段：`first_token_ms`、`duration_ms`、`request_type`（流式 / 非流式等）、`actual_cost` / `total_cost` / 账号成本、输入 / 输出 / 缓存 Token、`model` → `upstream_model` 映射、用户 / Key / 分组 / 账号、`request_id`。
  - 失败请求可用字段：`phase`、`error_owner`、`error_source`、`severity`、错误信息、上游重试链（`request-errors/:id/upstream-errors`）、`resolved` 与“标记已处理”（`PUT …/resolve`）、关联对象与 `request_id`。

### 默认处理（用户未反对）

- 用户列表排序与 Web 一致：**最新在前**（created_at 倒序）。
- “充值与调整记录”里的兑换条目显示**兑换码前 8 位**（同 Web）。
- Setup Token 账号凭据失效时主按钮是**“重新授权…”**（同 Web，Setup Token 与 OAuth 一样走重新授权）。
- MiniMax-01 这类过长的状态说明缩短，393pt 宽度下不截断关键信息。

### TPM 口径（2026-10-18，用户确认）

- **TPM 把缓存 Tokens 算进去**：首页 6 格的 TPM 与统计分析“RPM / TPM 趋势”同一口径（含缓存，演示 240K）。
- 数据来源：后端 dashboard/stats 的 tpm 只算 input + output（不含缓存），不能直接用；改取 admin/ops/dashboard/throughput-trend 最近一段的 token_consumed（含缓存）× 60 ÷ 实际覆盖秒数。站点没开运维监控时，首页 TPM 退回 dashboard/stats 的值并在规格里注明口径差异（或请后端在 dashboard/stats 增加含缓存的 tpm）——在最终规格里定。
- 统一措辞（主线收尾）：“成本”统一叫“**账号成本**”（首页今日区、账号详情今日）；受限说明里统一叫“**模型限流 N**”；监控 · 概况和 base 首页的“运行”区也不再写“近 5 分钟”（与评审第 1 条一致，口径不变）。
- 落地提醒：现有 App 的 DashboardView 首页 TPM 读 dashboard/stats 的 tpm（不含缓存），要改成 throughput-trend 最近 5 个 1 分钟桶 ÷ 5（含缓存）；PerformanceTrend.rate 要按每桶实际覆盖秒数折算（首尾不满一桶时不骤降）。
- 状态胶囊**相邻粘连**（用户补充）：原先贴边线挨在一起会连成一条，改成胶囊后要保留这个特性。用户看过后要求**不同色也连起来**：同一列表里紧挨着的几条，不论同色异色都连成一根连续的状态轨，交界处无缝、颜色直接切换，只有整段最上端和最下端是圆头。待处理、告警中、错误请求、分组列表等都生效。
