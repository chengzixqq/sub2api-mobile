## 0. 一页摘要

**核心主张（一句话）**：App 的根不再是“对象目录”，而是“问题队列”。打开 App 就能看到现在有什么需要处理、原因是什么、怎么一键处置；所有对象都从问题下钻进入。充值退款和看营收另走两条快车道，不经过问题队列，同样一两步就能到。

十个关键决定：

| # | 决定 | 一句话理由 |
|---|---|---|
| 1 | admin 的 Tab 为 **今日 · 账号 · 用户 · 渠道**（站点开启渠道监控时才有“渠道”），外加 **搜索**（`Tab(role: .search)`） | 四个 Tab 分别对应用户确认的四个高频任务。日志不占 Tab（用户原话），从问题和搜索进入 |
| 2 | “今日”页由三部分组成：一行**今日账本条**、**需要处理**收件箱、**运行概况** | 救火和看营收在同一屏。账本条永远排第一行，问题再多也不会把营收挤出首屏 |
| 3 | 收件箱由 Sub2Core 中的纯函数 `TriageEngine` 按**规则表**生成（§4.1.3） | 待处理项有明确定义，可以单测，将来也可以作为推送深链的落点（05 §4.14） |
| 4 | 每个列表都**需处理优先**：账号先列“需处理”分区，用户先列“待核对”，分组和渠道按健康排序，错误日志默认只看“未处理” | 只排序，不隐藏。正常对象仍在列表里，问题始终排在上面 |
| 5 | 账号状态由四个维度组成：管理状态 × 调度 × **限时运行状态（带倒计时）** × 有效期。处置动作紧贴原因显示 | 救火时最想知道的是“何时恢复、现在能不能恢复”（05 §4.2） |
| 6 | “测试”是首选处置动作，因为后端在测试成功后会**自动恢复**账号的运行状态。【核实：`handler/admin/account_handler.go:1341-1345` 调用 `RecoverAccountAfterSuccessfulTest`】 | 一个动作同时完成两件事：确认已经修好，并恢复调度 |
| 7 | 确认分为 L0–L4 五档，由 `ConfirmPolicy` 统一判定 | 可逆操作不打扰，资金和删除操作必须拦截，红色只用来表示危险 |
| 8 | 站点切换放在每个 Tab 根页面的**导航标题菜单**里，站点名常驻导航副标题 | 环境切换属于导航层（03 P20），不占内容区 |
| 9 | 低频模块收进搜索 Tab 根页面的**目录**，最多三组，另加一组“在 Web 中管理”，并有明确的收纳规则 | 不再保留“管理”目录 Tab，也避免目录沦为杂物抽屉（05 §5.3） |
| 10 | 契约由 Core 测试和展示层测试保证；文案 lint 拦截契约句；UITest 只断言**状态词典**里的词，不断言句子 | 防止界面再次变成“验收面板”（R2） |

## 1. 核心主张，以及它为什么能根治 R1–R6

### 1.1 主张展开

管理员掏出手机时，脑子里依次只有三个问题：**有没有东西坏了？坏在哪里、什么时候恢复？我现在能做什么？** 现有界面按对象组织（概览、账号、用户、管理、设置），管理员要自己在五个 Tab 之间拼出这三个答案。而且“异常账号 1”点不进去（01 D22），错误原因看不到（01 D03），恢复动作根本没有接入（02 §6.1-3）。

分诊优先把这三个问题直接做成 App 的骨架：

1. **问题是一等对象。** 一条“待处理项”包含对象、状态、原因、时间和处置动作。它由规则产生，不依附于某个页面。
2. **对象是问题的上下文。** 点开问题后才看到账号、用户或分组的详情；在详情里还能沿关联继续下钻（日志、分组、渠道）。返回时始终回到问题。
3. **处置紧贴问题。** 动作就显示在原因旁边。处置完成后，条目自动消失并移入“最近恢复”，形成闭环。

参考产品：PagerDuty（“我的未关闭事件”，滑动确认或解决）、Grafana IRM（Firing / Ack / Silenced 计数，加内联操作）、Linear Inbox（优先级队列，处理完自动进入下一项）、AWS Console 首页（告警计数卡和账单卡同屏），见 03 §2.2–2.7。

### 1.2 逐条根治 R1–R6

| 根因 | 现状（证据） | 分诊优先的结构性解法 | 防复发机制 |
|---|---|---|---|
| R1 用设置页范式承载数据 | insetGrouped List 加值灰化的 `LabeledValue`（01 D05） | 首屏元素全部采用“结论 + 动作”结构：收件箱卡、状态先行的行、详情页的“问题头卡”。键值对只出现在详情末尾的 `PropertyGrid` 里，值用主色。`Form` 只用于录入 | 组件清单删除 `LabeledValue`；PR 检查清单要求详情首屏不出现键值行 |
| R2 契约文案出现在界面上 | 60 多条契约句；185 个 identifier 用于断言文字（01 §4 R2） | 分诊界面只说三类话：**是什么问题、为什么、怎么处置**。契约改由组件状态表达：缺失值显示“—”，结果不明显示待核对横幅，精度交给统一格式化器；这些都在 Sub2CoreTests 中断言 | 文案 lint（§12.4）；UITest 只断言 `StatusVocabulary` 中的词 |
| R3 缺少语义层 | 原始枚举直接显示，“不可用”出现 42 处，6 种以上色相没有语义（01 D09–D11） | 分诊必须给每个对象一个**严重度**和一个**状态词**，这就迫使我们建立唯一的 `StatusVocabulary`：状态 → 中文词 → 语义色 → 符号 → 徽章优先级 → 分诊严重度 | lint 禁止 `Text(x.rawValue)`；词典与 Web 的 zh 语言包做快照比对（04 §4.1 末段） |
| R4 数据层缺口 | 限时状态未解码，恢复动作未接入（02 §6.1） | 收件箱规则表**直接列出**每条规则依赖的字段和接口（§4.1.3）。没有这些数据就没有收件箱，所以补齐数据是 P0，不是“以后再说” | §9 的 P0 清单是阶段 1 的准入条件 |
| R5 信息架构碎片化 | 分析有 4 个入口；“管理”是目录 Tab；要手输 ID；“异常账号 1”点不进去（01 D14/D22/D23） | 入口只有三种：**从问题进入、从搜索进入、从关联进入**。所有计数都可以点击，并携带预置筛选；日志由问题带着条件打开；对象筛选用搜索 token 代替手输 ID；切换站点就在标题上 | 收纳规则（§2.5.3）；路由表 `Route` 是唯一的导航入口 |
| R6 操作语义失当 | 10 个确认全部用 destructive；有 3 种提交范式；sheet 套 sheet；没有触觉反馈（01 D07/D15、05 §4.10） | 动作紧贴问题；`ConfirmPolicy` 分五档；反馈只有三种形态（toast、原位错误、待核对横幅），配固定的触觉；一次只出现一个 sheet；所有编辑统一在导航栏“保存” | `ConfirmPolicy` 的单测覆盖每个动作的档位；lint 禁止在 Feature 里直接写 `role: .destructive` |

### 1.3 “推到极致”的边界

**推到极致的部分**

- **0 次点击看到问题，1 次点击处置。** 首屏就是收件箱，卡片上直接有“测试 / 恢复状态 / 标记已处理”。
- **队列式处理。** 从收件箱打开详情页时，导航栏右侧会出现 ⌃⌄（“上一项 / 下一项 2/5”），处理完不必返回列表。Mail 和 Linear Inbox 也是这样做的。
- **闭环。** 条件消失的条目会自动移入“最近恢复”（折叠显示，保留 60 分钟），而不是悄悄消失。
- **需处理优先贯穿每个列表**（见决定 #4）。
- **Tab 徽标只计“紧急”和“待核对”。** HIG 要求徽标只用于关键信息（03 §1.1）。
- **倒计时实时走动。** 限流、过载和临时不可调度会在行内显示恢复倒计时，归零后自动刷新该对象。

**护栏：不牺牲非救火任务**

- **账本条固定在“今日”第一行**，约 1.5 行高，不会随问题增多而下沉；点一下即可进入统计分析。
- **“用户”保留为一级 Tab**，根页面就是常驻的搜索框。充值和退款在三处都有入口：用户行的滑动操作、用户详情首屏、搜索结果（§3.2）。
- **收件箱清零时不显示空页。** 清零后，“运行概况”会展开为今日趋势图和健康数字（§4.1）。
- **浏览不受打扰。** “全部账号”“全部用户”随时可看，不需要先清空收件箱；需处理优先只影响排序。

**刻意不做的部分**

- 不隐藏正常对象（只排序，不过滤）。
- 不自造后端没有的“认领 / 确认（ack）”状态。告警事件只有“解决”和“静默”两种操作【核实：`ops_alerts_handler.go:444` 只接受 `resolved`、`manual_resolved`】，账号也没有 ack。唯一的本机状态是“稍后”（在本机隐藏 1 小时），菜单文案就直接写“在本机隐藏 1 小时”。
- 不承诺推送。后端只有邮件，没有出站推送（02 §5），所以收件箱是拉取式的，推送只预留深链落点（§11.3）。

### 2.1 底部 Tab（admin，本轮）

| Tab | 根页面 | SF Symbol | 徽标 | 出现条件 | 承接的高频任务 |
|---|---|---|---|---|---|
| 今日 | `TodayView`：账本条、收件箱、运行概况 | `tray.full` | 紧急项与待核对项之和（为 0 时不显示） | 始终出现 | 救火入口，早晚看营收 |
| 账号 | `AccountsRoot`：需处理分区和全部账号 | `server.rack` | 无（避免与“今日”重复计数） | 始终出现 | 救火（浏览与批量操作） |
| 用户 | `UsersRoot`：常驻搜索框、待核对、最近处理、全部用户 | `person.2` | 无 | 始终出现 | 充值、退款 |
| 渠道 | `ChannelsRoot`：渠道健康列表 | `waveform.path.ecg` | 无 | `channel_monitor_enabled` 不为 false | 看渠道监控 |
| 搜索 | `FinderRoot`：跨对象搜索和目录 | 系统放大镜 | — | 始终出现 | 日志和低频模块的入口 |

- 渠道监控关闭时，Tab 为“今日 · 账号 · 用户”外加搜索。HIG 允许 3 到 5 个 Tab，不必为了凑数再加一个。
- 删除现有的“管理”和“设置”两个 Tab（01 D23、03 §1.1）。“概览”改名为“今日”，内容也从“指标墙”变成“问题 + 账本”。
- Tab 标签一律用两个汉字，在 iPhone 上不会被截断。

### 2.2 是否使用 `Tab(role: .search)`：使用

- **用途**：跨对象查找，包括用户邮箱、账号名、分组名、API Key 名和请求 ID；同时承载低频模块的目录。它是“从问题下钻”之外唯一的直接入口，用来解决“得先猜对东西在哪个 Tab”的问题（03 §1.1）。
- **实现**：`Tab(value: .search, role: .search) { NavigationStack(path: $router.search) { FinderRoot() } }`，并在 `TabView` 上加 `.tabViewSearchActivation(.searchTabSelection)`。按 03 §1.1 引用的第三方证据，在 iOS 27.2 上如果不加这个修饰符，搜索 Tab 会退化成普通 Tab，失去独立的浮动按钮。
- **代价与验证点（原型验证 V1）**：`.searchTabSelection` 会在选中 Tab 时直接聚焦搜索框并弹出键盘，目录只能露出上半部分。应对办法有两个：一是把目录的前两组（“最近”和“常用”）放在最上方；二是加 `.scrollDismissesKeyboard(.immediately)`，一滑动就收起键盘。如果真机体验不好，就退回 `.automatic` 激活方式，接受“普通 Tab + 导航栏搜索”的外观，信息架构不变。
- 列表页内的 `.searchable`（账号名、用户）继续保留，和搜索 Tab 不冲突：列表内搜索是在当前对象类型里过滤，搜索 Tab 用于不知道东西在哪的时候。

### 2.3 Tab 由“角色 + 站点能力”推导

Tab 集合和目录项都由 Sub2Core 中的纯函数推导，不在视图里写死：

```swift
public struct ShellSpec: Equatable, Sendable {
    public var tabs: [AppTab]                    // 有序，最多 4 个，不含搜索
    public var directory: [DirectorySection]
    public var triageRules: Set<TriageRuleID>
}
public enum ShellRole: Sendable { case admin, vendor(VendorGrants), user }
public struct SiteCapabilities: Equatable, Sendable {
    public var opsMonitoring: Bool               // 运维监控：告警、错误日志、可用性、健康分
    public var channelMonitor: Bool              // 渠道监控
    public var payment: Bool, subscription: Bool, riskControl: Bool, affiliate: Bool
}
public extension ShellSpec {
    static func make(role: ShellRole, capabilities: SiteCapabilities) -> ShellSpec
}
```

**能力来源**

| 能力 | 来源（02 章节） | 字段未返回时 |
|---|---|---|
| `channelMonitor` | `GET settings/public` → `channel_monitor_enabled`（02 §1.6）。Web 的 `utils/featureFlags.ts` 把它当作 opt-out | 视为开启；如果接口返回禁用错误，降级为 `FeatureOffState` |
| `payment` / `subscription` / `riskControl` / `affiliate` | `settings/public` → `payment_enabled`、`subscription_enabled`、`risk_control_enabled`、`affiliate_enabled`【核实：Web `utils/featureFlags.ts:97-133` 注册了这些键】 | 视为关闭（按 opt-in 处理，避免出现空壳） |
| `opsMonitoring` | `GET admin/settings` → `ops_monitoring_enabled`（02 §1.6），与 Web `stores/adminSettings.ts:64` 同源。只解码这一个布尔值，不缓存其他设置 | 视为开启；任何 ops 接口返回 `OPS_DISABLED` 时置为关闭 |
| vendor 权限档 | `GET admin/workspaces/me`（02 §1.2“工作区”），权限档包括 `account_manage`、`group_ops`、`group_billing`、`proxy_manage`、`monitor_view`（05 §4.1） | 本轮不开放 vendor，见 §11 |

**三种角色的 Tab 集合**

| 角色 | Tab（最多 4 个）+ 搜索 | 推导条件 | 期次 |
|---|---|---|---|
| admin | 今日 · 账号 · 用户 · 渠道，外加搜索 | “渠道”仅在 `channelMonitor` 为真时出现 | 本轮 |
| vendor（代运营） | 今日 · 账号 · 分组，外加搜索 | “账号”需要 `account_manage`；“分组”需要 `group_ops` 或 `group_billing`；代理（`proxy_manage`）放进目录。没有用户、渠道、运维，因为 vendor 访问这些接口会得到 403（02 §1.6） | 以后 |
| user（普通用户） | 首页 · 密钥 · 用量 · 我的，`channelMonitor` 为真时再加“渠道状态” | 用户端没有跨对象搜索的需求，不设搜索 Tab | 以后 |

**推导规则**

1. 只在会话建立时推导：登录、切换站点，或从后台恢复且能力发生变化时。会话进行中能力变了，Tab 也不会闪动，而是在下次回到前台时生效，并用 toast 提示，例如“站点已开启渠道监控”。
2. 能力关闭时，对应的 Tab 和目录项都不生成，不出现“即将推出”“未开启”这类空壳入口（简报约束 7）。如果从旧深链或关联跳进已关闭的模块，显示 `FeatureOffState`（§6）。
3. 至少保留 2 个 Tab。超过 4 个时，优先级最低的移入搜索目录（admin 不会出现这种情况）。
4. 登录接口返回的 `role` 决定 `ShellRole`。本轮 vendor 和 user 仍然在登录时被拦截，但拦截文案要按角色区分（§4.16）。

### 2.4 站点切换放在哪里

- **每个 Tab 根页面**都使用 `.navigationTitle("账号")` + `.navigationSubtitle("主站")` + `.toolbarTitleMenu { … }`。点击标题（系统会显示 ⌄）弹出站点菜单：
  ```
  ✓ 主站              admin@main
    备用站            ops@backup
    ─────────────────────────────
    添加站点…
    站点与账户…        （进入设置页）
  ```
- “今日”根页面的副标题是“主站 · 刚刚更新”，其他根页面只写站点名。副标题前用一个小图标显示站点 Logo，取自 `settings/public` 的 `site_logo`（05 §4.12）；没有 Logo 时，用站点名首字的圆形标记代替。
- 详情页不放站点菜单，防止在对象深处切换站点。所有 L2 和 L3 确认的标题或说明里都要写出站点名（§5.2）。
- 切换站点本身属于 L0，不需要确认。例外情况：当前站点有“进行中的写入”或“本会话待核对项”时，弹出非 destructive 确认，提示“切换后，主站的待核对事项会保留在收件箱中”。
- 切换完成后：所有 Tab 的导航路径清空，`sessionGeneration` 换代（沿用现有的守卫机制，01 §7.1）；“今日”页先显示骨架，加载完成后 toast 提示“已切换到 备用站”。

#### 2.5.3 收纳规则（防止目录沦为杂物抽屉）

1. **Tab 里已有的，目录里不再放。** 账号、用户、渠道不进目录；日志不是 Tab，所以放进目录。
2. **能挂在对象上的，不进目录。** 订阅挂在用户和分组上，代理优先挂在账号上，兑换码的“补偿”挂在用户上。目录只收“没有自然宿主”的模块。
3. **原生分组最多三组，另加一组 Web。** 原生组固定为“常用 / 运维 / 商业”，vendor 再多一组“资源”。如果需要第四组，说明某个模块应该挂到对象上，或者应该留在 Web。
4. **每个模块必须明确归为“原生 / 原生只读 / 仅 Web”之一**，归类写在 `DirectoryEntry.kind` 中。“仅 Web”的项一律带 ↗，用 `openURL` 打开站点后台的对应路径（Web 路由见 04 §3.1），不用 WebView 内嵌。
5. **按角色和能力裁剪。** 目录项和 Tab 共用 `ShellSpec.make` 的判断，视图层不得另写可见性逻辑。
6. **不放空壳。** 尚未实现的模块不出现在目录里，也不写“即将推出”。
7. **计数只显示可点击的精确数字。** 例如“23 条未处理”直接取自接口的 `total`；算不准的数字不显示。

## 4. 逐屏规格

### 4.0 所有屏幕共用的约定

- **导航标题**统一用 inline（`.navigationBarTitleDisplayMode(.inline)`），省下大标题占用的约 19% 首屏（01 D41）。唯一例外是“站点与账户”页。
- **分层**：内容层不透明，使用系统 grouped 背景和 `secondarySystemGroupedBackground` 卡片。Liquid Glass 只用在 Tab 栏、导航栏、`FilterBar`、`SelectionActionBar` 和浮动 toast 上（03 §1.10）。
- **列表容器**：日志、账号、用户这类列表用 `List` + `.listStyle(.plain)`；详情页用 `.insetGrouped` + `.listSectionSpacing(.compact)`。坚持用 `List`，是为了拿到滑动、选择和上下文菜单（05 §6.3）。
- **数字**：一律加 `.monospacedDigit()`。金额、Token 和时间只能通过 `Formatters`（§8）输出。缺失值显示“—”，VoiceOver 读作“未返回”。
- **语义色**（简报 §2；04 §4.1）：绿色表示正常，琥珀色表示限流、临时或接近上限，红色表示错误、过载或不可用，灰色表示停用、暂停或未知，紫色表示模型级限流。颜色一律与**符号形状**一起使用：✓ 正常，● 错误，▲ 警告，‖ 暂停，⊘ 停用，◆ 模型限流，◷ 待核对。
- **新鲜度**：每页只保留一个新鲜度标记。“今日”页放在导航副标题，其余页面放在列表底部的 `MetaText`。
- **首次加载**：用骨架屏（`.redacted(reason: .placeholder)`），不用带文字的 ProgressView。

**合并、排序与身份**

- **合并**：同一条规则命中超过 3 个对象时，合并成一条，例如“5 个账号错误”。卡片显示前 3 个名称再加“等”，主动作改为“查看全部”，严重度取其中最高的。
- **排序**：先按严重度（紧急 > 待核对 > 警告 > 提示），再按开始时间由新到旧。
- **稳定 ID**：`"{规则}:{对象类型}-{对象ID}"`，例如 `T3:account-42`、`T2:event-9001`。它同时用于“稍后”、“最近恢复”、accessibilityIdentifier，以及将来的推送 payload。
- **T1 与 T3–T6 可能指向同一批账号**：T1 只提供分组视角，不吞并账号条目。这样做可以避免为了去重而写复杂逻辑。【推断：这种重叠在真实站点上是否扰人，要在原型中观察。】

**刷新节奏**：前台时，快速源每 60 秒刷新一次（stats、三个账号状态查询、可用性）；慢速源每 180 秒刷新一次（告警、错误计数、健康分、渠道、趋势）。离开“今日”页或进入后台时暂停，下拉刷新会刷新全部。倒计时在本地计算，并做服务器时钟偏差校正（§9 P1-20）。

#### 4.1.4 卡片解剖

```
┃ ●  上游A · 错误                 12 分钟前
┃    401 · invalid x-api-key
┃    [测试]  [恢复状态]                    ⋯
↑     ↑            ↑                       ↑
严重度条 对象 + 状态词（取自词典）   开始时间的相对表示；限时状态改为倒计时
```

- **严重度**：左侧 4pt 色条加一个符号（● 紧急，▲ 警告，◷ 待核对，○ 提示），形状和颜色同时编码。
- **标题行**：对象名用 `.headline`，后接状态词。状态词只给文字上语义色，不铺整块色底。右侧显示相对时间或倒计时（`.monospacedDigit()`）。
- **原因行**：只占 1 行（`.lineLimit(1)`），长按或进入详情可以看全文。错误信息一律先经过 `RequestLogPresentation.safeMessage` 脱敏（01 §6.1）。
- **动作行**：最多 2 个 `.bordered` 小按钮，加一个 ⋯ 菜单（打开对象、复制、在本机隐藏 1 小时）。合并后的条目只有“查看全部”一个按钮。
- **整卡点击**：以“队列模式”打开对象详情。
- **动态字号**：在辅助功能字号下，动作行折成两行，原因行可以展开到 3 行；不缩小字号。

#### 4.1.5 操作入口

- **卡片**：内联按钮是主入口。前缘滑动执行卡片的主动作（`allowsFullSwipe: false`）；后缘滑动是“稍后”（在本机隐藏 1 小时）；长按弹出上下文菜单，包含卡片动作、打开和复制。
- **账本条**：点击进入统计分析（今日、全站）。
- **运行概况**：每个数字都可以点击，在“今日”的导航栈里 push 对应页面。“账号可用”进入 `Route.accountList(.attention)`，“渠道”进入渠道列表，“错误率”进入“日志 · 失败”。
- **工具栏**：不放额外按钮。刷新靠下拉，切换站点靠标题。

#### 4.1.6 状态呈现

- **首次加载**：账本条显示骨架，收件箱显示 3 张骨架卡。
- **部分失败**：某个数据源失败时，收件箱顶部出现一行 `SectionFailure`，例如“告警暂时无法读取 · 重试”，其他规则照常显示。**读不到不等于没有问题**：只要有数据源失败，就不允许显示“一切正常”。
- **全部失败**：显示 `ErrorState` 和“重试”；账本条保留上次的数据，并标上 `StaleBanner`。
- **运维监控关闭**：不显示 T1、T2、T8、T10，T4 也不带账号名。收件箱底部显示一行 `FeatureOffHint`：“站点未开启运行监控，告警与错误不会出现在这里 · 在 Web 中开启 ↗”。⋯ 菜单里可以选择“不再提示”。
- **清零**：显示一行“一切正常”，运行概况展开（见 4.1.2）。

**行解剖**

```
[符号] 名称（headline，单行尾部截断）               [状态词 · 倒计时]
       平台显示名 · 首个分组(+n) · 认证类型        [最紧张维度的容量条 + n/m] 或 [今日 1.2K 次 · $3.40]
       原因（只有需处理的行才有；1 行，次要色）
```

- **状态符号**：✓ 正常（绿）、● 错误或过载（红）、▲ 限流、临时不可调度或配额超限（琥珀）、‖ 暂停（灰）、⊘ 停用或已过期（灰）。◆ 模型级限流（紫）只作为附加标记。
- **第二行右侧**：二选一，在 ⋯ 菜单里切换，按站点身份保存，复用 `ListFieldSelection` 的存储。
  - “容量”（默认）：取最紧张的那个维度，即并发、RPM、窗口费用、日/周/总配额中占用比例最高的一项，用 `Gauge(.accessoryLinearCapacity)` 加“3/4”显示。≥75% 显示琥珀色，≥90% 或已满显示红色（04 §4.1#24）。全部缺失时显示“—”。
  - “今日用量”：今日请求数和实际扣费。这是 RN 端迭代中体现出的偏好（04 §2.6#2）。
- **取消“显示字段”编辑器**（01 D25）：原先 23 个可选字段收敛为固定的三行，外加一个二选一偏好。
- **动态字号**：在辅助功能字号下，第二行右侧的内容移到第三行；平台和分组只保留平台。

**分区与数据**

- **“需处理”分区**：并行查询 `status=error`、`rate_limited`、`temp_unschedulable`（每路 `page_size=50`），再加上可用性接口中的过载账号。在本地合并去重，先按严重度、再按倒计时排序。如果某个状态的 total 大于已取到的数量，就在分区末尾加一行“还有 N 个限流账号 ›”，点击进入该状态的完整列表。
- **“其他账号”分区**：沿用现有分页的 `admin/accounts`（默认按名称排序），跳过已经出现在“需处理”分区的 ID。
- **单一状态筛选**：选中某个状态后，列表变成单个平铺列表，不再分区。

**筛选项**

- **状态**：全部（需处理优先）/ 需处理 / 正常 / 错误 / 限流中 / 临时不可调度 / 停用 / 暂停，与 Web 一一对应（04 §4.1#8）。其中“暂停”对应 Web 筛选项中的“不可调度”，见附录 Q3。
- **平台**：使用显示名。
- **分组**：包含“未分组”。
- **类型**：OAuth / Setup Token / API Key / AWS Bedrock 等。
- 过载在服务端没有对应的筛选值（02 §3.1C），所以不提供这个筛选项，过载账号只出现在“需处理”分区里。

**操作入口**

- **导航栏**：左侧“选择”，进入批量模式（§4.6）。右侧是筛选按钮（有生效条件时显示 `.badge(n)`）和 ⋯ 菜单（行内显示：容量 / 今日用量；在 Web 中新建账号 ↗）。
- **行滑动**：前缘为“停止调度 / 启用调度”（L1）；后缘为“测试”，以及“恢复状态”（仅在可恢复时出现）。
- **长按菜单**：打开、测试、恢复状态、停止或启用调度、编辑…、查看上游错误、复制名称。
- **列表内搜索**：`.searchable(placement: .navigationBarDrawer(displayMode: .automatic))`，下拉时出现，按名称搜索，沿用 300ms 防抖（01 §7.7）。

**状态呈现**

- 首次加载显示 6 行骨架。
- 筛选后为空时，显示 `EmptyState.filtered`：“没有符合条件的账号 · 清除筛选”。
- “需处理”分区为空时，整个分区不出现，不写“没有需处理的账号”。
- 某个状态查询失败时，在分区标题下显示一行 `SectionFailure`。
- 倒计时归零时，该行显示“恢复中…”，并单独刷新这个账号。

- **二次验证**：服务器要求二次验证时，`StepUpInline` 出现在表单顶部，验证通过后需要再点一次“保存”。

**行解剖**

- **请求行**（请求视图）：
  ```
  14:32  ✓  claude-sonnet-4.5                 $0.0124
            alice@ex… · 上游A · 流式 · 1.25s
  ```

  左列是时间（HH:mm，等宽）和结果符号。右侧是实际扣费：不低于 $0.01 时保留两位小数，低于 $0.01 时保留到 4 位（沿用 `DashboardPresentation.cost` 的规则，05 §4.6）。用户显示为邮箱，不再显示“#8”（05 §4.6）。请求类型用中文（流式 / 同步 / WS / Live / 安全策略，04 §4.1#15）。
- **错误行**（失败视图和上游错误视图）：左列是时间加 HTTP 状态码。4xx 和 429 用琥珀色，5xx 用红色。状态码后面跟错误分类的中文名（04 §4.1#16）。右侧是处理状态。

**对象筛选（替代手输 ID）**

- **机制**：`.searchable(text:tokens:placement:prompt:token:)` 配合 `.searchSuggestions`。输入“ali”时，建议按类型分组显示：
  - 用户：`usage/search-users?q=`，返回 id、email、deleted，最多 30 条【核实：`handler/admin/usage_handler.go:380-409`】；
  - API Key：`usage/search-api-keys?q=&user_id=`，返回 id、name、user_id，最多 30 条【核实：同文件 `:415-450`】；
  - 账号：`admin/accounts?search=&lite=1`；
  - 分组：在本地过滤 `groups/all`；
  - 模型：取 `dashboard/models` 在当前时间范围内出现过的模型名；
  - 如果输入看起来像请求 ID，显示“按请求 ID 查找 “4f2a…””。
- **token**：选中建议后生成一个 token（`LogToken`：`.user(id, email)`、`.apiKey(id, name)`、`.account(id, name)`、`.group(id, name)`、`.model(name)`、`.requestID(s)`）。token 与现有 `RequestLogFilter` 的字段一一对应，管理员不再需要输入任何 ID。
- **切换来源时不再悄悄丢条件**：上游错误视图只支持时间、账号、分组和状态码。切到上游错误时，它不支持的 token 仍然留在原处，置灰并标注“此来源不支持”，但**不会被删除**；切回其他来源时自动恢复生效。这修正了 05 §2#3 指出的“上游模式会静默删除筛选条件”。
- **时间胶囊**：菜单项为 近 1 小时 / 近 24 小时 / 近 7 天 / 近 30 天 / 自定义…。预设是滚动窗口，下拉刷新时会更新到当前时间；“自定义”打开日期选择 sheet，选定后是固定范围，胶囊显示为“10/15 01:33–10/16 01:33 ×”（01 C59/C60）。
- **其他胶囊**：失败和上游错误视图有“状态码”（429 / 4xx / 5xx / 指定码）和“处理状态”（未处理 / 已处理 / 全部）；请求视图有“类型”。

| 收件箱条目 | 卡片的主动作（测试 / 恢复状态 / 标记已处理 / 核对） | 稍后（在本机隐藏 1 小时） | 主动作、次动作、打开对象、复制，分隔线后为“在本机隐藏 1 小时” | 对象状态卡 |
| 账号行 | 停止调度 / 启用调度 | 测试；可恢复时另有“恢复状态” | 打开、测试、恢复状态、停止或启用调度、编辑…、查看上游错误、复制名称 | 状态卡（状态、原因、容量） |
| 用户行、用户搜索结果 | 充值… | 退款… | 充值…、退款…、查看请求记录、查看失败请求、复制邮箱，分隔线后为“禁用用户…” | 余额卡 |
| 请求行 | — | — | 复制请求 ID、查看用户、查看账号、按此用户 / 账号 / 模型筛选 | — |
| 失败 / 上游错误行 | 标记已处理 / 标记未处理 | — | 同请求行，另加“标记已处理” | — |
| 分组行 | — | — | 查看账号、查看失败请求，分隔线后为“停用…”或“启用” | — |
| 渠道行 | — | — | 查看组内账号、查看失败请求、分组详情 | — |

**规则**

1. 所有滑动都设置 `allowsFullSwipe: false`，防止误触（03 P13 中的 GitHub 案例）。
2. 会写入服务器的滑动操作只允许 L1 级别。打开 sheet 的操作（“充值…”“退款…”）本身不写入，可以放在滑动里。L2 及以上的操作不放滑动。
3. 滑动操作与菜单的前几项保持一致（HIG：“Match top menu actions to swipe actions”）。菜单里的每一项，在详情页的主界面上也要有入口（HIG Context menus）。
4. 当前不可用的菜单项直接隐藏，不置灰（HIG Context menus）。
5. 需要后续输入的菜单项，名称后加“…”。
6. destructive 项放在菜单最后，并用分隔线隔开。
7. 选择模式下不提供滑动操作。
8. 长按只是快捷方式，不能是某个操作的唯一入口（03 A15）。

### 5.2 确认分级

| 档 | 判定条件 | 界面 | 例子 | 是否 destructive |
|---|---|---|---|---|
| **L0** | 不写服务器，或只改本机状态 | 不确认 | 筛选、切换站点（没有进行中的写入时）、复制、在本机隐藏、金额遮罩 | — |
| **L1** | 写服务器，单个对象，可逆或无害 | 直接执行。界面先显示“正在停止…”，成功后 toast（可逆的带“撤销”）；失败则原位回滚，并 toast 报错 | 单个账号停止或启用调度、标记错误已处理或未处理、恢复状态、编辑后保存、启用用户、启用分组、手动解决告警 | 否 |
| **L2** | 可逆的批量操作；或单个对象但有成本、会影响他人 | `confirmationDialog`。标题为“动词 + 对象 + 数量”，按钮为“动词 + 数量”，**不用 destructive**；从触发按钮处弹出 | 批量停止或启用调度、批量恢复状态、批量刷新凭据、重置配额、刷新凭据、静默告警（让用户选时长）、禁用用户、停用分组 | 否；后果写在说明文字里 |
| **L3** | 资金、不可逆或删除 | 在 sheet 中复核金额和对象，再弹 `confirmationDialog`，按钮为 destructive，并写明站点、对象和金额 | 充值、退款、删除分组、删除站点和凭据、退出并清除凭据 | 是 |
| **L4** | 后端要求二次验证 | 在当前 sheet 内用 `StepUpInline` 完成验证，然后回到原按钮再确认一次，不自动重放 | 创建管理员、把用户提升为管理员（02 §1.6），以及任何返回二次验证要求的写入 | 沿用其基础档位 |

- 档位由 Core 中的 `ConfirmPolicy.level(for: ActionKind, count: Int) -> ConfirmLevel` 决定，视图不能自己选择按钮的 role。
- **会影响他人的可逆操作升一档**：禁用用户、停用分组本身可逆，但会立即影响他人，所以从 L1 升为 L2。这是对简报约束 5 的细化，见附录 Q6。
- 批量确认的说明里最多列 3 个名称，其余写“等 N 个”，避免确认框需要滚动（03 P15）。
- 按钮标题要描述结果，例如“停止调度（3 个）”“充值 $50.00”，不使用“确认”“确定”“确认发送”。
- “静默告警”属于“带选项的确认”：`confirmationDialog` 中给出“静默 30 分钟 / 1 小时 / 到今天结束”三个按钮，请求体为 `rule_id`、`platform`、`group_id`、`until`、`reason`【核实：`ops_alerts_handler.go:476-481`】。
- 在 iOS 27 上，可以用 `#available(iOS 27, *)` 改为 `confirmationDialog(_:item:)`。

### 5.3 成功、失败、待核对的反馈

| 结果 | 形态 | 触觉 | 持续时间 | 位置 |
|---|---|---|---|---|
| 成功（L1 / L2） | toast：过去式动词 + 对象，可带“撤销” | `.sensoryFeedback(.success, trigger:)` | 4 秒；带撤销时 6 秒 | Tab 栏上方；在 sheet 内则位于 sheet 底部 |
| 成功（L3 资金） | toast，同时详情里的数字做过渡动画 | `.success` | 4 秒 | 同上 |
| 明确失败 | 原位回滚，并在行内显示错误；同时 toast，例如“未能停止调度 · 重试” | `.error` | 6 秒，或直到用户操作 | 原位和底部 |
| 待核对 | 持久的 `ReconcileBanner`，同时进入收件箱 T11 / T12，并显示底部附件 | `.warning` | 直到核对完成 | 页面顶部；底部附件跨页面显示 |
| 读取失败 | 分区内的 `SectionFailure`，或页面级的 `StaleBanner` | 无 | 一直显示 | 原位 |
| 选择或切换 | — | `.selection` | — | 分段控件、胶囊、勾选 |

- 只有用户自己的操作结果才触发触觉；后台刷新带来的数据变化不触发。
- 取消现在的全局 alert“操作未完成”（01 D40）。只有阻断性的会话错误才用 alert，并写清楚原因，例如“登录已过期，请重新登录”，按钮为 [重新登录]。其他错误都按上表处理。
- toast 出现时，用 `AccessibilityNotification.Announcement` 播报。

### 5.4 撤销

- **只用于可逆操作**：L1 中的停止或启用调度、标记已处理或未处理、编辑后保存（按字段撤销）、启用用户或分组；以及 L2 中唯一可撤销的批量调度。
- **撤销的实现**：发送一个反向的写请求，而不是在本地回滚。这个请求有自己的成功和失败反馈；撤销失败时 toast“未能撤销 · 重试”。
- **同一时刻只保留一个可撤销的 toast**：新的操作出现时，上一个撤销即失效。
- **不提供撤销的操作**：资金、删除、恢复状态、手动解决告警、测试。它们要么不可逆，要么没有反向语义。恢复状态之后如果问题依旧，账号会重新出现在收件箱里，这本身就是反馈。
- **VoiceOver**：toast 显示期间，可以用“魔法轻点”（`.accessibilityAction(.magicTap)`）触发撤销。

### 5.5 未保存草稿的保护

- 所有编辑类 sheet（账号、用户、分组、创建用户、充值和退款）都加上 `DraftGuard`：设置 `.interactiveDismissDisabled(isDirty || isSubmitting)`；有修改时点“取消”，弹出 `confirmationDialog`“放弃未保存的修改？”，选项为 [放弃修改]（destructive）和 [继续编辑]。
- 在充值或退款 sheet 中，只要输入了金额就算有修改。
- 草稿只保存在内存里，不跨启动保留。例外是已经提交的余额请求，它按现有机制持久化。
- sheet 打开时，Tab 栏和标题菜单都被遮住，所以无法在编辑中途切换站点。
- 搜索和筛选的输入不算草稿。

### 5.6 sheet 使用规则

1. **一次只出现一个 sheet**（HIG）。sheet 内部需要的后续步骤（选分组、选对象、二次验证、核对）都在 sheet 自己的 `NavigationStack` 里 push，或者就地展开。不再像现在这样在 7 处各自挂一个 StepUpView（01 §6.2）。
2. **sheet 只承载有明确终点的小任务**：编辑、充值或退款、测试、批量结果、自定义时间范围、创建、验证码。浏览和详情一律用 push。
3. `confirmationDialog` 和 `alert` 可以出现在 sheet 之上，因为它们本身不是 sheet。
4. **从 sheet 跳到别的对象**时，先关闭 sheet，再在下层的导航栈里 push（`router.dismissThenPush(route)`）。
5. **detent**：测试和批量结果用 `[.medium, .large]`；编辑、充值和创建用 `[.large]`。不自定义 `presentationBackground`（iOS 26 指南，03 §1.6）。
6. **每个根视图只维护一个 sheet 状态**：一个 `@State var sheet: SheetRoute?`，配合 `.sheet(item:)`。

### 5.7 返回栈与跨对象跳转

```swift
enum Route: Hashable, Codable {
    case account(Int), accountList(AccountQuery), user(Int), userList(UserQuery)
    case group(Int), groupList, channel(ChannelKey)
    case logs(LogQuery), request(RequestRef), error(ErrorRef)
    case analytics(AnalyticsScope), alerts, alert(Int), settings, help(HelpTopic)
}
```

- 每个 Tab 各有一个 `NavigationStack(path: $router.paths[tab])` 和 `.navigationDestination(for: Route.self)`。
- **跨对象跳转只在当前 Tab 的栈内 push，不切换 Tab。** 这修正了 codex 原型的倒退（05 §5.6）。例如从“今日”打开账号，返回时回到收件箱。
- **去重**：如果目标对象已经在当前路径里，就 pop 回那一层，而不是再 push 一次。这样可以打破现状中可以无限压栈的环（01 §1）。
- **深度上限 10**：超过时丢掉最早的中间层，保留根页面和最近的 9 层。
- **队列导航（⌃⌄）**：从收件箱进入时，路由会附带 `queueContext`（收件箱快照中的 ID 列表）。切换到下一项时**替换栈顶**，而不是 push。
- **重复点击当前 Tab**：先 pop 回根页面；已经在根页面时，再点一次则滚到顶部。
- **切换站点**：清空所有路径（会话换代）。
- **深链（预留）**：`sub2://<站点ID>/account/<id>`。如果站点不同，先切换站点，再选中“今日”Tab，然后 push 对应页面。

### 5.8 刷新与新鲜度

- 以下拉刷新为主，每页一个 `.refreshable`。删除所有分区上的“刷新××”按钮（01 D19）。
- **前台轮询**：“今日”采用 60 秒 / 180 秒两档；账号列表 60 秒一次，选择模式下暂停；渠道 120 秒一次。离开页面或进入后台时暂停（沿用 01 §7.3）。
- **每页一个新鲜度标记**：使用 `Text(.currentDate, format: .reference(to: updatedAt))`（iOS 18），显示为“刚刚更新”“3 分钟前更新”（03 P17）。
- 刷新失败时显示 `StaleBanner`，不清空已有内容。

| 待核对 | `ReconcileBanner` + `PendingAccessory` | 写入结果不明 | 页面顶部持久横幅，带动作；底部附件 | “充值 $50.00 待核对 · 核对” | `.warning` 触觉加播报 |

**规则**

1. **读不到不等于没有。** 数据源失败时，不得显示“一切正常”或“0”。
2. 每个 `AsyncSection` 独立加载、独立失败，复用从 `DashboardLoadState` 抽出的通用加载状态（01 §6.2）。
3. 状态组件是这些状态**唯一**的呈现方式。Feature 视图里不再手写 `ProgressView("…")` 或红字错误行（01 D29）。
4. 状态文案只说业务：“暂时无法读取”“未开启”“无权查看”。不提接口、快照或刷新机制。

## 7. 账号状态模型

### 7.1 四个维度

| 维度 | 字段（02 §3.1） | 取值 → 中文 / 语义色 / 符号 | 管理员能做什么 |
|---|---|---|---|
| 管理状态 | `status` | active → 正常 / 绿 / ✓；inactive 或 disabled → 停用 / 灰 / ⊘；error → 错误 / 红 / ● | 错误时可以“测试”或“恢复状态” |
| 调度开关 | `schedulable` | true → 参与调度；false → 暂停 / 灰 / ‖ | 启用或停止调度（L1） |
| 限时运行状态 | `rate_limit_reset_at`；`overload_until`；`temp_unschedulable_until` + `temp_unschedulable_reason`；`extra.model_rate_limits`；配额的 used ≥ limit；`session_window_status` | 限流中 / 琥珀 / ▲ + 倒计时；过载中 / 红 / ● + 倒计时；临时不可调度 / 琥珀 / ▲ + 原因 + 倒计时；模型限流 / 紫 / ◆（附加标记，按模型列出）；配额超限 / 琥珀 / ▲；会话窗口接近上限 / 琥珀，已满 / 红 | 恢复状态；重置配额 |
| 有效期 | `expires_at`、`auto_pause_on_expired` | 72 小时内到期 → “n 天后过期”（附加标记）；已过期 → 已过期 / 灰 / ⊘，如果自动暂停，同时显示“暂停” | 在 Web 中续期 ↗ |

由 Core 中的纯函数推导：

```swift
public struct AccountCondition: Equatable, Sendable {
    public var admin: AdminState            // .active / .inactive / .error(message)
    public var schedulable: Bool
    public var blocks: [RuntimeBlock]       // .rateLimited(until) / .overloaded(until) / .tempUnschedulable(until, reason)
                                            // .modelRateLimited([ModelLimit]) / .quotaExceeded(dimension) / .sessionWindow(level)
    public var expiry: Expiry               // .none / .expiringSoon(date) / .expired(autoPaused: Bool)
    public var primary: StatusTerm          // 主徽章（7.2）
    public var secondary: [StatusTerm]      // 附加标记，最多显示 1 个，其余显示为“+n”
    public var triage: TriageSeverity?      // 分诊严重度（7.3），nil 表示不需处理
    public var recoveries: [RecoveryAction] // 7.6
    public static func derive(_ account: UpstreamAccount, now: Date) -> AccountCondition
}
```

### 7.2 主徽章的判定顺序（与 Web 完全一致，04 §4.1#6）

```
限流中 / 过载中 → 错误 → 临时不可调度 → 非 active（停用 / 已过期）→ 配额超限 → 暂停 → 正常
```

- **附加标记**：模型限流、暂停、即将过期。主徽章是“错误”时不再附加“暂停”，因为后端在设置错误时会同时把 `schedulable` 置为 false（02 §3.1A），再显示“暂停”只会让人困惑。
- **未知取值**：遇到未知的 status 时显示“未知”（灰色），不显示原始英文（修正 02 §3.1A 中 `disabled` 没有映射的问题）。

### 7.3 分诊严重度（用于排序，与徽章分开）

| 条件 | 严重度 | 是否进入“需处理” |
|---|---|---|
| 错误、过载中 | 紧急 | 是 |
| 临时不可调度、限流中、配额超限、会话窗口已满 | 警告 | 是 |
| 模型限流（账号仍可调度） | — | 否，只作附加标记 |
| 72 小时内过期 | 提示 | 否，只在收件箱出现（T7） |
| 停用、暂停（人为操作） | — | 否 |
| 正常 | — | 否 |

徽章顺序沿用 Web，以保证两端的心智模型一致；严重度单独定义，用于决定排序和是否进入收件箱。两者分开，才能既与 Web 一致，又让最需要人工处理的错误排在最前面。

### 7.4 倒计时

- `CountdownText(until:)`：剩余不到 1 小时时，用 `Text(timerInterval:countsDown:)` 显示 mm:ss；1 小时以上显示“14:30 恢复”；跨日显示“明天 09:00 恢复”。
- **时钟校正**：根据响应头 `Date` 计算服务器时钟偏差（§9 P1-20），倒计时 = until − (now + offset)。
- **归零时**：显示“恢复中…”，并单独刷新这个账号（防抖 5 秒）。刷新后如果仍然受限，就显示新的截止时间。
- **VoiceOver**：读作“限流中，2 分 14 秒后恢复”，不逐秒播报；只在获得焦点时读取 `.accessibilityValue`。

### 7.5 在行、详情和筛选中的呈现

| 状态 | 列表行 | 详情 | 筛选项 |

## 10. iPad：本轮“能用”，后期深度适配

### 10.1 本轮做到“能用”

- **`.tabViewStyle(.sidebarAdaptable)`**：iPad 横屏时显示侧栏，竖屏或分屏时可以切换成顶部 Tab 栏。侧栏用 `TabSection` 分成三组：“值班”（今日、账号、渠道）、“客户”（用户）、“工具”（日志、统计分析、分组）。“工具”组的条目加 `.defaultVisibility(.hidden, for: .tabBar)`，只在侧栏出现；在 iPhone 上，它们仍然在搜索目录里。
- **列表与详情双栏**：每个 Tab 根页面包一层 `AdaptiveSplit`：`horizontalSizeClass == .regular` 时使用 `NavigationSplitView { 列表 } detail: { NavigationStack(path:) { 详情 } }`，compact 时使用 `NavigationStack`。“今日”在左栏显示收件箱、右栏显示当前条目的对象详情，队列导航变成左栏的选中项。
- **sheet**：在 iPad 上以表单样式呈现，使用 `.presentationSizing(.form)`（iOS 18）。
- **本轮不做**：多列表格、检查器、键盘快捷键。只保证不出现被拉伸的单列列表，列宽由分栏约束。
- **验收**：iPad 模拟器在横屏、竖屏和 1/3 分屏下的截图，纳入每个阶段的验收。

### 10.2 为后期深度适配预留

| 能力 | 计划 | 预留点 |
|---|---|---|
| 多列表格 | 日志、账号改用 `Table`，多列可排序，用 `TableColumnCustomization` 保存列设置 | 行组件带 `density` 参数，单元格可以复用行内子视图 |

### 12.2 UITest 重写成本

- **现状**：7 个文件、35 个用例、1,617 行。大量按控件类型查询元素：`textFields` 25 次，`switches` 15 次，`segmentedControls` 6 次（05 §4.15）；另有 185 个 identifier（01 附录 B）。
- **预计**：
  - `AccountListCustomizationUITests`（字段编辑器）整体删除，换成 1 个“行内显示偏好”的用例。
  - `RequestLogsUITests` 中断言 ID 输入框的部分，全部重写为 token 筛选。
  - `UserManagementUITests` 中的余额流程重写。
  - `AccountManagementUITests` 中的选择、批量和编辑重写。
  - `GroupsUITests` 和 `AnalyticsUITests` 做结构性调整。
  - `Sub2MobileUITests`（登录和概览）重写。
  - 【推断】约 80% 的用例需要重写，约 1,200–1,500 行。UITest 随各阶段的功能一起重写，不集中到最后再补；每个阶段预留约 30% 的工时给 UITest。旧用例在所属阶段内先标记为跳过，而不是删除，阶段结束前补齐。
- **方法**：
  - 使用 Page Object（`InboxScreen`、`AccountListScreen`、`BalanceSheetScreen` 等），把 identifier 集中在一个地方。
  - 夹具场景化：每个场景对应 §6 中的一个状态，或 §3 中的一条任务路径。

### 12.3 accessibilityIdentifier 策略

- **只给两类元素加 identifier**：可交互元素，和承载状态的元素。说明性文字不加 identifier，新设计里本来也不应该有这类文字。
- **命名格式**：`<屏幕>.<元素>[.<对象键>]`，对象键使用服务器 ID 或分诊的稳定 ID。例如：`today.ledger`、`inbox.item.T3-account-42`、`inbox.item.T3-account-42.action.test`、`accounts.row.42`、`accounts.row.42.status`、`account.header.recover`、`balance.amount`、`balance.submit`、`toast`、`toast.undo`、`filter.chip.time`、`logs.token.account-42`。
- **断言什么**：状态元素的 `label` 必须等于 `StatusVocabulary` 中的词。UITest target 链接 Sub2Core，直接引用词典常量，不断言句子。金额的期望值也由 `Formatters` 生成。
- **契约语义移到单元测试**：缺失不等于 0、不自动重放、精度、待核对时锁定等，移到 Sub2CoreTests 和 `WriteCoordinator` 的测试中。UI 测试只验证状态，例如“出现了待核对横幅”“按钮被禁用”。

### 12.4 防止“契约文案”回流

1. **文案 lint**（`scripts/check-ui-copy`，在 CI 和提交前运行），扫描 `NativeApp/**/*.swift` 中的字符串字面量：
   - **禁词**：接口、快照、自动重放、不会自动、幂等、前台每、独立加载、未以、不以、原始精度、IPA、确认发送、确认执行、确认操作，以及作为值出现的“不可用”。
   - 以“。”结尾且超过 20 个字的 `Text` 字面量，必须位于 `HelpCatalog` 或白名单中。
   - `Text(….rawValue)`，以及插值中出现 `.rawValue`。
   - Feature 目录中出现 `.font(.footnote)` 或 `.font(.caption)`（这两种字号只允许在组件目录中使用）。
   - Feature 中直接写 `role: .destructive`（必须经过 `ConfirmPolicy`）。
2. **文案只有三个来源**：`StatusVocabulary`（状态词）、动作文案表（`ActionKind.title`，即动词）、`HelpCatalog`（口径说明，只在 ⓘ 和“术语与口径”页中出现）。新增说明性文字必须放进 `HelpCatalog`，并经过评审。
3. **验收不看屏幕上的句子**：`docs/ACCEPTANCE.md`、`docs/ADMIN_MODULES.md` 中的契约条款，逐条映射到 Core 测试的名称（在 PR 模板中列出这份映射），而不是映射到 identifier。
4. **评审清单增加一问**：“这句话是在说用户的业务，还是在说我们的实现？”
