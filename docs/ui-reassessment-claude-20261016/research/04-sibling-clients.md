## 0. 核心结论

1. **【事实】RN 端最后只保留 3 个 Tab（概览 / 用户 / 服务器）**。账号不再是 Tab，而是从概览里的「账号概览」健康卡片下钻进入；分组页虽然有路由，但已经没有任何入口（`RN/app/(tabs)/_layout.tsx:32-61`；提交 `3177500`）。**【推断】** 迭代方向说明：顶层越少越好，账号应该按"健康状况 → 问题清单"的方式进入。
2. **【事实】RN 在迭代中持续往"高频运维动作前置、减少层级"的方向调整**：删掉了账号详情页，把「测试 / 暂停-恢复」直接放到列表卡片上；卡片指标从配置字段（并发、倍率）换成今日运营数据（请求、消费、Token）；状态词从「暂停」改成了「限流」（提交 `434bbf2`、`a054a44`、`3177500`）。
3. **【事实】RN 留下的主要问题**：账号状态压缩成「正常 / 暂停 / 异常」三态，和 Web 的状态体系不一致；分页写死 20 条，统计却在这 20 条上做，"限流"计数不准，界面上还直接写出了实现细节；每一行单独请求统计（N+1）；表单里要手填 JSON、要输入逗号分隔的 ID；存在两个重复且没有入口的「添加账号」页；原始英文状态直接展示；资金操作没有二次确认。
4. **【事实】Web 后台已经形成一套很细的心智模型**：账号状态有 11 个状态词，并有固定的判定优先级；颜色语义是 绿=正常、琥珀=限流/临时、红=错误/过载、灰=停用/暂停、紫=模型级限流；成本有三种口径（实际扣费=绿、成本=橙、标准=灰）；延迟分 4 档并有固定阈值；错误类型有 6 种颜色；运维健康分以 90/60 为分界。这些属于移动端**必须照搬的语义层**（出处见 §3、§4.1）。
5. **【事实】Web 自身的用词也不统一**：账号/账户、错误/异常、停用/禁用/已禁用、独占/专属、渠道监控里两套状态词、分组停用显示红色而账号停用显示灰色。移动端要先建一份统一术语表，逐条裁决（§5）。
6. **【事实】Web 在窄屏下的降级方式是把每一行变成"列名：值"逐行罗列的卡片**（`WEB/components/common/DataTable.vue:8-90`）。当前原生端的账号列表正好就是这种形态（`SHOT/AccountManagementUITests/0FE95C0E-…png`）。**【推断】** 这是"丑、反人类"观感的主要来源之一。移动端在信息结构上应该和 Web 刻意不同：先给摘要再下钻、按优先级展示字段，而不是把列逐一铺开。
7. **【事实】原生端已经和 Web 出现用词偏差**：inactive 显示为「已禁用」，Web 是「停用」；error 显示为「异常」，Web 是「错误」；筛选项用「可调度」，Web 是「正常」；请求类型直接显示 `stream`，Web 是「流式」；平台直接显示 `openai`，Web 是「OpenAI」（`NAT/Sources/Sub2Core/AccountPresentation.swift:86-87`、`NAT/NativeApp/Features/AccountsView.swift:215-217`、截图 `SHOT/RequestLogsUITests/9A6FA137-…png`）。

**账号清单（`RN/src/screens/accounts-list-screen.tsx`）**

### 2.4 做得好的地方
1. **顶层精简加按健康状况下钻**：概览上的账号健康卡就是进入账号列表的入口（`monitor.tsx:328-361`），管理员从"有没有问题"自然走到"哪个有问题"。
2. **状态筛选胶囊直接带计数**（`accounts-list-screen.tsx:153-171`），不用打开筛选面板就能看到分布。
3. **高频动作内联**：「测试」「暂停 / 恢复」直接在卡片上，各行独立显示进行中状态，结果就地回显（`:247-290`）。
4. **卡片优先展示运营指标**（今日请求、消费、Token）而不是配置项；错误信息用红字直接展示，不需要悬停（`:227-245`）。
5. **加载、空、错误、未配置四种状态都有**，并附带可执行的按钮（`monitor.tsx:289-313`）。
6. **危险操作走系统 Alert 并带 destructive 样式**；不可执行的操作会说明原因（管理员不能被禁用）（`users/[id].tsx:358-374`、`:447`）。
7. **复制有瞬时反馈**（`users/[id].tsx:181-196`、`:350-356`）。
8. **多服务器切换做成卡片，切换后自动检测连通性**（`settings.tsx:121-136`）。
9. **视觉辨识度高**：暖纸色配深青绿，在一众系统灰的管理 App 中容易认出（`RN/docs/mobile.jpg`）。**【推断】** 这一点属于主观审美，可以作为"不要退回纯系统默认风格"的参照。

### 2.5 暴露的问题（应避免重蹈）
1. **统计口径不准，还把实现细节写到了界面上**：限流和繁忙只基于第一页 20 条账号计算（`monitor.tsx:187-192`、`:222-231`；`RN/src/services/admin.ts:148-151` 写死 `page_size: 20`），说明文字原样展示给用户（`monitor.tsx:359`）。git 记录显示，`a054a44` 曾改为拉取全部账号（`listAllAccounts`），随后 `293b62b` 又退回只取第一页。**【推断】** 原因是性能，代价是数字不可信。
2. **没有分页**：用户、账号、分组都只取 20 条（`services/admin.ts:90-93`、`:138-151`）；筛选和排序只作用于这 20 条，因此筛选胶囊上的计数是错的（`accounts-list-screen.tsx:104-136`）。
3. **N+1 请求**：每个账号单独请求 today-stats（`accounts-list-screen.tsx:82-88`），每个用户单独请求 usage stats（`users.tsx:171-178`）。Web 用的是批量接口 `getBatchTodayStats` / `getBatchUsage` / `listWithEtag`（见 `WEB/views/admin/AccountsView.vue` 中的调用）。
4. **状态模型过度简化**：三态无法区分限流中、临时不可调度、过载、配额超限，与 Web 的 11 个状态词不一致（`accounts-list-screen.tsx:14-50`，对照 `WEB/i18n/locales/zh/admin/accounts.ts:443-463`）。
5. **直接展示原始英文值**：`admin · active · name`（`users.tsx:121`）、StatusBadge 原样输出 status（`users/[id].tsx:169-179`、`:428`）、`platform · type` 原值（`accounts-list-screen.tsx:213`）。
6. **概览变成图表墙**：7 个以上的图表卡纵向堆叠，图表无法交互，「趋势摘要」与折线图内容重复（`monitor.tsx:363-439`）。
7. **存在死页面和重复页面**：分组页不可达；两个「添加账号」页标题相同且都没有入口；其中一个挂在 `users/` 路由下，会混淆"用户"和"上游账号"（`RN/app/_layout.tsx:116-154`）。
8. **表单面向开发者**：需要手填 JSON，用逗号分隔 ID，标签里中英混写字段名（`accounts/create.tsx:258`、`:279`；`users/create-account.tsx:356-460`）。
9. **资金操作风险**：金额默认填 10，可选「设为」，提交前没有确认，也没有幂等保护（`users/[id].tsx:243`、`:330-348`）。原生端已有确认对话框和幂等编号（`NAT/NativeApp/Features/UsersView.swift:462`、`:489`）。
10. **删掉账号详情后能力也丢了**：`3177500` 删除了 `accounts/[id].tsx`，「刷新凭据」（`refreshAccount`）、账号 7 日趋势、并发等信息从此没有地方展示。
11. **测试反馈太简陋**：只显示「测试成功」或一条错误文本，不能选择模型，也看不到延迟和输出（`accounts-list-screen.tsx:254-261`）。Web 的测试弹窗能选模型、看实时输出、复制结果（`WEB/components/admin/account/AccountTestModal.vue:61-69`、`:180-210`）。

### 3.10 Web 管理员已经形成的心智模型
- **对象**：「账号」= 上游 AI 账号（菜单「账号管理」）；「用户」= 平台客户；「分组」= 路由与计费单元；「API 密钥」= 用户的 Key；「渠道」= 对外的模型通道；「代理」在菜单里叫「IP 管理」。
- **状态**：账号有 11 个状态词并有固定优先级（§3.3）；用户是启用 / 禁用；分组是正常 / 停用；渠道是可用 / 性能下降 / 不可用；告警是告警中 / 已恢复。
- **颜色**：绿=正常 / 可用；琥珀=限流 / 临时 / 偏慢 / 接近上限；橙=成本 / 账号认证 / 缓存 1h；红=错误 / 过载 / 不可用 / 严重；灰=停用 / 暂停 / 未知；紫=模型级限流 / 路由 / 输出 Token。
- **数字口径**：成本固定三元「实际 / 成本 / 标准」；Token 拆成输入、输出、缓存读、缓存写；延迟是「首字 / 总耗时 / TPS」。
- **筛选维度**：时间 × 平台 × 分组 × 账号 × 用户 × 模型 × API Key × 类型 / 状态码 / 错误分类。
- **常用操作**：测试连接、启用 / 停止调度、恢复状态 / 重置状态、刷新令牌 / 重新授权、充值 / 退款、启用 / 禁用用户、查看统计、跳转到该用户的使用记录、标记错误已解决。

### 4.3 旧版 RN 端：值得借鉴与应当避免

**值得借鉴**
1. 用概览上的健康卡作为进入账号列表的入口（`monitor.tsx:328-361`）。【推断】即使账号继续占一个 Tab，概览上也应保留"异常 n / 限流 n"的可点击入口，并带着筛选条件跳过去。
2. 状态筛选胶囊带计数（`accounts-list-screen.tsx:153-171`）。
3. 列表上直接放「测试」「暂停 / 恢复」，各行独立显示进行状态，结果就地回显（`:247-290`）。
4. 卡片展示今日运营数字，而不是配置项（迭代信号 §2.6-2）。
5. 错误信息用红字内联显示（`:245`）。
6. 时间分段下方显示解析后的日期区间（`monitor.tsx:285`）。
7. 加载、失败、未配置三种状态都给出可执行的按钮（`monitor.tsx:289-313`）。
8. 危险操作用系统 Alert 并标 destructive；不可执行的操作说明原因（`users/[id].tsx:358-374`、`:447`）。
9. 复制后有「已复制」的瞬时反馈（`:181-196`）。
10. 服务器做成卡片，切换后自动做连通性检测（`settings.tsx:59-136`）。
11. 有明确视觉个性（暖底配深青绿），没有使用纯系统默认风格（`docs/mobile.jpg`）。

**应当避免**
1. 统计基于第一页，还把口径说明写到界面上（§2.5-1）。数字要么来自后端聚合，要么明确标注统计范围，不能悄悄算错。
2. 分页写死，只在客户端做筛选（§2.5-2）。
3. 每行一个统计请求（§2.5-3）。应使用批量接口，与 Web 一致。
4. 自创的三态状态模型（§2.5-4）。
5. 直接显示原始英文值（§2.5-5）。
6. 图表墙，且图表静态不可交互（§2.5-6）。
7. 留下没有入口的死页面，或重复的页面（§2.5-7）。
8. 需要填 JSON、逗号分隔 ID 的开发者式表单（§2.5-8）。
9. 金额预填默认值，提交前没有确认（§2.5-9）。
10. 为了少一层而把详情页整个删掉，导致刷新凭据等能力丢失（§2.5-10）。正确做法是：高频动作前置，同时保留详情页。
11. 每个文件各自定义颜色常量（§2.1）。

### 4.4 管理员在手机上最可能的真实任务（均为【推断】）
依据：两端的功能分布、RN 的迭代方向、Web 已有的深链与快捷入口。

| # | 场景 | 典型路径 | 依据 |
|---|---|---|---|
| S1 | **收到投诉或告警后判断"是不是上游挂了"**（最高频） | 概览上的异常/限流数 → 带筛选的账号列表 → 账号详情（错误信息、恢复时间）→ 测试连接 → 恢复状态或停止调度 | RN 健康卡下钻与"暂停→限流"的改动（§2.6-5）；Web 的状态判定、恢复状态、测试连接 |

| S3 | **某用户反馈请求失败或扣费不对** | 搜索用户 → 该用户的错误请求 / 用量明细 → 请求详情（复制请求 ID、上游状态码、错误分类、三种成本） | Web 的 `user_id` 深链（`UsageView.vue:320`）、仪表盘消费榜跳转（`DashboardView.vue:626`）、错误请求 Tab |
| S4 | **客服式充值或退款** | 搜索用户 → 余额 → 充值 / 退款 → 备注 → 确认 | Web 余额单元格内联「充值」（`UsersView.vue:451-457`）；RN 详情页的余额操作 |
| S5 | **早晚巡检** | 概览：今日请求、Token、实际扣费 / 成本、RPM/TPM、健康分、错误率趋势 | RN 概览；Web 仪表盘第一、二行；Ops 头部 |
| S6 | **处置滥用用户，或帮用户排查 Key** | 用户 → 禁用（需确认）/ 查看 API Key 并复制 / 查看分组 | RN 用户详情；Web 行操作 |
| S7 | **OAuth 凭据过期** | 账号详情 → 刷新令牌；若需要重新授权，则跳到 Web 或系统浏览器完成 | Web「重新授权 / 刷新令牌」（`AccountActionMenu.vue:40-49`）；【推断】完整授权流程不适合在 App 内完成 |

**【推断】排序含义**：S1–S5 应该是一级入口能直接完成的任务，最多点 3 下；S6–S8 允许多一层。新建账号、改分组定价、系统设置都不在这个清单里，可以交给 Web。
