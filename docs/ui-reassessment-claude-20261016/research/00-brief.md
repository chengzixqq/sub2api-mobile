## 2. 调研结论摘要（详见 01–05）

- 根因 R1：用“系统设置页”范式（insetGrouped List/Form + 键值行，值为灰色）承载监控/排障/账务数据；iOS 26 把列表行高进一步加大，更稀。
- 根因 R2：界面被当作“验收面板”——60+ 条验收契约原句写在界面上，185 个 accessibilityIdentifier 让 UITest 断言这些文字。**新设计必须明确：契约由单元测试/展示层测试保证，不得以界面说明文字的形式存在。**
- 根因 R3：无语义层——无状态词典、原始英文枚举直出、“不可用”42 处、6+ 色相无语义、10 个确认全部 destructive。
- 根因 R4：数据层缺口——账号限时运行状态（`rate_limit_reset_at`、`overload_until`、`temp_unschedulable_until/reason`、`model_rate_limits`）未解码；恢复动作（clear-error、clear-rate-limit、清除临时不可调度、recover-state、reset-quota）未接入；后端已有告警事件、`ops/account-availability`、`health_score`、错误 `resolved`、渠道监控 V2、余额流水、`usage/search-users` / `search-api-keys` 等可直接支撑新界面。
- 根因 R5：信息架构碎片化——日志埋在“管理”目录页、统计分析 4 个入口、切站只在设置、筛选手输数字 ID、“异常账号 1”不可点、无跨实体搜索。
- 根因 R6：操作语义失当——确认不分级、3 种提交范式、成功结果写成常驻分区、sheet 套 sheet、无触觉反馈。
- 身份：存在 admin / vendor（代运营）/ user 三种角色；站点功能开关（ops 监控、渠道监控、支付、订阅等）决定模块是否存在 → **Tab 与模块入口应由“角色 + 站点开关”推导，而不是写死**。
- 术语与语义色以 Web 为准（见 04 §4.1、§5 的裁决表）：账号 inactive=停用、error=错误、调度动作=启用调度/停止调度、暂停状态=暂停；绿=正常、琥珀=限流/临时/接近上限、红=错误/过载/不可用、灰=停用/暂停/未知、紫=模型级限流；成本三口径 实际/成本/标准。**视觉身份可自由，但语义色的含义必须稳定**（色值可按新视觉调校）。

## 3. 设计硬约束

1. 技术：SwiftUI，最低 iOS 26；系统外壳（TabView 玻璃底栏、NavigationStack、toolbar、sheet、search、menu、swipe、contextMenu）全部用原生；**Liquid Glass 只用于导航/控件层，内容层不透明**（HIG Materials）。
2. 保留并复用逻辑层：`Sources/Sub2Core`、会话代际守卫、写入安全语义（不自动重放、结果不明=待核对、余额幂等编号持久化、二次验证后需重新确认）、Decimal 精度、分区独立加载。
3. 允许并应当列出 UI 所需的数据层补充（上面 R4 列出的字段与接口），按优先级排期；不得虚构后端不存在的能力（如推送——后端只有邮件，没有出站推送）。
4. 文案规范：界面只说业务，不说接口/实现；缺失值显示“—”（VoiceOver 读“未返回”）；不用原始英文枚举；动词用业务词（“暂停调度”“充值”而不是“确认发送”）。
5. 确认分级：可逆单对象操作直接执行并提供撤销/反馈；可逆批量操作用非 destructive 确认；资金/不可逆/删除用 destructive 并写明对象与金额；高风险沿用二次验证。
6. 必须覆盖的难点界面：日志对象筛选（替代手输 ID）、账号编辑、余额充值/退款、批量逐项结果、结果待核对、加载/失败/空状态、登录与切站、账号测试（流式）。
7. 身份扩展：admin 本轮；vendor、普通用户以后——结构上要能按角色裁剪，不预先摆空壳入口。
8. 可访问性：Dynamic Type（含辅助功能字号）、VoiceOver、深浅色、增强对比度、减弱动态效果；点击区 ≥44pt；状态不只靠颜色。
9. 交付形态：设计必须能用 SwiftUI + 演示数据在模拟器上原型化（下一轮会真的在 Mac 上编译运行并截图）。
